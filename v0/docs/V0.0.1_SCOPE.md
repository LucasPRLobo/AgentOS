# AgentOS Platform — v0.0.1 Scope

> Defines exactly what ships in v0.0.1 and what is deferred. This is the contract between ideation and implementation.

---

## Product Summary

**v0.0.1 is a local-first, no-auth, horizontal multi-agent platform** where users build agent teams through a visual DAG builder or pre-built templates, configure agent behavior in plain English or with advanced LLM settings, connect to any model provider (cloud API keys, managed access, or local Ollama), and monitor execution in real time.

No accounts. No billing. No cloud infrastructure. Users run the platform locally and bring their own model access. The focus is entirely on the core product experience: **build a team, configure agents, run the workflow, watch the results.**

## What Ships in v0.0.1

### 1. Visual Workflow Builder

A drag-and-drop canvas for designing agent workflows as directed graphs.

**Scope:**
- Drag agent nodes from a palette onto the canvas
- Draw edges to define execution order and data flow
- Click any node to open its configuration panel
- **Linear sequences** (A → B → C) and **parallel fan-out/fan-in** (A → [B, C] → D)
- Zoom, pan, minimap for navigation
- Undo/redo for canvas operations
- Real-time workflow validation (no cycles, connections valid, configs complete)
- Save/load workflows as JSON files (local filesystem, no cloud persistence)

**NOT in scope:** Conditional branching, loops, sub-workflows, dynamic agent spawning. These require a more complex execution engine and builder UI — deferred to v0.0.2.

**Data model:**
```
Workflow {
  id: string
  name: string
  description: string
  version: string
  nodes: [{
    id: string
    role: string              // role template name or custom
    position: { x, y }
    config: {
      model: string           // model identifier
      system_prompt: string
      persona_preset: string  // "formal", "creative", etc.
      tools: string[]         // enabled tool names
      budget: { max_tokens, max_tool_calls, max_time_seconds }
      advanced: { temperature, top_p, max_output_tokens }
    }
  }]
  edges: [{
    source: string            // node id
    target: string            // node id
    data_contract: {          // optional inter-agent schema
      output_schema: object   // JSON Schema for source output
      input_schema: object    // JSON Schema for target input
    }
  }]
  variables: [{               // workflow-level inputs
    name: string
    type: string
    default: any
  }]
}
```

**Tech:** React Flow (@xyflow/react) for the canvas. Workflow JSON persisted to local filesystem via the API.

### 3. Natural Language Workflow Creation

Users describe what they want in plain English. An LLM generates a workflow.

**Scope:**
- Text input field: "Describe the agent team you want to build"
- LLM generates a complete workflow JSON (nodes, edges, configs)
- Generated workflow appears in the visual builder for review and editing
- Refinement: user can follow up with adjustments ("add a reviewer at the end", "use GPT-4 for the writer")
- Works with any capable model the user has access to (GPT-4, Claude, etc.)

**Implementation approach:**
- Structured output via native API (function calling / tool_use) to generate valid workflow JSON
- Validation layer between LLM output and the builder: fix cycles, validate tool references, enforce constraints
- System prompt includes: available tools, available models, example workflows, the workflow JSON schema
- Fallback: if generation fails, suggest the closest matching template

**NOT in scope:** Conversational multi-turn workflow design assistant. v0.0.1 is single-shot generation + manual refinement in the builder.

### 4. Agent Persona Studio

Layered configuration interface for defining agent behavior.

**Scope:**

**Simple mode (default view):**
- Role name and description
- Behavior instructions in plain English textarea
- Personality presets dropdown: Formal, Creative, Analytical, Concise, Friendly
- Model selector (populated from available models)
- Tool permissions: checkboxes for which tools this agent can access

**Advanced mode (toggle):**
- Temperature slider (0.0–2.0)
- Max output tokens slider
- Top-p slider
- System prompt editor (raw text, syntax-highlighted)
- Response format: free text / JSON / markdown
- Few-shot examples editor: add input/output pairs

**NOT in scope:** Reusable saved personas, persona versioning, persona marketplace, test sandbox (chat with agent in isolation). Deferred to v0.0.2.

### 5. Model Access Layer

Support for all three model access patterns.

**Scope:**

**BYOK (Bring Your Own Key):**
- Settings page where users enter API keys for OpenAI and Anthropic
- Keys stored locally (config file on disk, not cloud)
- Per-agent model selection: any model from configured providers
- Supported providers: OpenAI (GPT-4o, GPT-4o-mini, o1, o3-mini), Anthropic (Claude Sonnet, Opus, Haiku)

**Local models (Ollama):**
- Auto-detect Ollama on localhost (already built)
- List available models from Ollama API (already built)
- Per-agent model selection from local models

**Managed access:**
- Platform provides model access via a proxy endpoint
- Users don't need their own API keys
- Rate-limited to prevent abuse (no billing in v0.0.1, so usage caps instead)
- Implementation: platform server proxies requests to a configured backend (OpenRouter, or direct API with platform's keys)

**Model capability profiles:**
- Track which models support structured output natively (function calling, tool_use)
- Track context window sizes per model
- Display in model selector: "GPT-4o — 128K context, structured output supported"
- Warn users when selecting a model that may struggle with the workflow requirements

**NOT in scope:** Fine-tuned model hosting, model performance benchmarking, model cost comparison dashboard.

### 6. Structured Output Enforcement

Use native model APIs instead of raw text parsing where possible.

**Scope:**
- **OpenAI**: Use function calling / response_format for agent actions
- **Anthropic**: Use tool_use blocks for structured agent responses
- **Ollama/local**: Fall back to the resilient text parser (already built) with JSON mode when supported
- **Adapter pattern**: Each model provider implements a `generate_structured()` method that returns typed `AgentAction` objects
- **Automatic protocol selection**: Platform detects model capabilities and chooses the best output strategy

**Architecture:**
```
BaseLMProvider
  ├── generate(prompt) → raw text         (existing)
  └── generate_structured(prompt, schema)  (new)
        ├── OpenAIProvider   → function_call / response_format
        ├── AnthropicProvider → tool_use blocks
        └── OllamaProvider   → JSON mode + resilient parser fallback
```

### 7. Inter-Agent Data Contracts

Schema validation and context management between agents in a pipeline.

**Scope:**
- **Output schemas** — Each agent can declare the structure of its output (JSON Schema)
- **Input schemas** — Each agent can declare what it expects from upstream
- **Validation** — After agent N finishes, validate its output against the edge's data contract before passing to agent N+1
- **Validation failure handling** — Auto-retry agent N with "your output didn't match the expected format" prompt (up to 2 retries), then fail the edge with a clear error
- **Context window management:**
  - Track token count of each agent's output
  - If output exceeds next agent's available context budget, automatically summarize using the same model
  - Context budget = model's context window - system prompt - tool schemas - safety margin (10%)
- **Data transformation** — Basic built-in transforms: extract JSON from markdown, truncate to N tokens, select specific fields from JSON output

**NOT in scope:** Complex data transformation nodes (non-LLM nodes in the DAG), user-defined transformation functions.

### 8. Live Monitoring Dashboard

Real-time view of workflow execution.

**Scope:**
- **DAG visualization** — Nodes color-coded by state (gray=pending, blue=running, green=done, red=failed)
- **Agent detail panel** — Click any node to see:
  - Current state (idle, thinking, tool call, done, failed)
  - Step counter: "Step 5 of max 50"
  - Budget usage bars (tokens, tool calls, time)
  - Last tool call with input/output preview
  - Full message history (LLM conversation log)
- **Event log** — Scrollable, real-time event stream
  - Color-coded by event type
  - Filter by agent and event type
  - Search within event payloads
- **Session controls** — Stop button, elapsed time display
- **Per-session cost display** — Total tokens used, estimated cost based on model pricing

**NOT in scope:** Historical cost trends, budget alerts, session comparison, export to CSV/JSON. Deferred to v0.0.2.

### 10. Agent Communication

**Pipeline data flow (Layer 1):**
- Each agent's output is injected into the next agent's prompt
- Structured handoff via data contracts (see section 7)

**Shared workspace (Layer 2):**
- All agents in a workflow share a workspace directory
- Agents can read/write files to the workspace
- Workspace browser in the UI shows all artifacts produced during the run
- Artifact viewer: click a file to preview its contents (text, markdown, images, CSV)

**NOT in scope:** Direct agent-to-agent messaging (Layer 3). Deferred to v0.0.2.

---

### 11. Error Handling

**Scope:**
- **Parse error retry** — If an agent's response can't be parsed, retry with a clarifying prompt (up to 3 times)
- **Tool failure retry** — If a tool call fails, retry with error context (up to 2 times)
- **Model fallback** — If the primary model returns an error (rate limit, outage), fall back to a configured backup model
- **Graceful failure** — If an agent exhausts retries, mark it as FAILED, log the error, and stop downstream agents
- **User notification** — Failed agents show red in the DAG with the error message visible on click

**NOT in scope:** Human approval gates, LLM-as-judge quality scoring, configurable retry policies. Deferred to v0.0.2.

## What is NOT in v0.0.1

### Deferred to v0.0.2

| Feature | Reason for deferral |
|---------|-------------------|
| Conditional branching + loops | Requires significant DAG engine and builder UI changes |
| Human approval gates | Requires notification infrastructure and async pause/resume |
| LLM-as-judge quality scoring | Doubles LLM cost per run; needs calibration |
| Agent persistent memory | Requires memory store, injection logic, and management UI |
| Scheduled runs (cron) | Requires background scheduler and run queue |
| Team workspaces | Requires auth + multi-tenancy |
| Detailed cost breakdown (per-agent trends) | Basic per-session cost is enough for v0.0.1 |
| Reusable saved personas | Need persona library, versioning, sharing |
| Agent test sandbox | Chat-with-agent-in-isolation requires standalone agent runner UI |
| Session replay + comparison | Event-sourced data is there; replay UI is extra work |
| No-code tool builder | REST API → tool requires UI for auth config, schema mapping, testing |

### Deferred to v0.0.3+

| Feature | Reason for deferral |
|---------|-------------------|
| User accounts + auth | Cloud infrastructure, not needed for local-first |
| Credits system + billing | Requires payment infrastructure (Stripe, etc.) |
| Public marketplace | Requires accounts, moderation, payment |
| Event-driven triggers (webhooks, email) | Requires always-on infrastructure |
| Knowledge base (RAG) | Requires embedding pipeline, vector store, retrieval |
| Direct agent messaging | Requires message routing, subscription model |
| Full flow control (sub-workflows, dynamic spawn) | Complex execution engine changes |
| View-only sharing | Requires shareable URLs, access control |
| Developer integrations (GitHub, Jira, DBs) | Each integration is significant work |
| Workflow optimization recommendations | Requires usage analytics engine |
| A/B testing for workflows | Requires experiment tracking infrastructure |
| Real-time collaboration | Requires CRDT or OT for concurrent editing |
| Mobile experience | Responsive web is fine for v0.0.1 |
| Agent collaboration patterns (debate, ensemble) | Advanced orchestration patterns |

## Key Technical Decisions

### Workflow Persistence (v0.0.1)

Local filesystem, not database. Workflows saved as JSON files in a configurable directory (`~/.agentos/workflows/`). Simple, no auth needed, easy to version control (users can git-track their workflows).

API:
```
POST   /api/workflows          → save workflow JSON
GET    /api/workflows          → list saved workflows
GET    /api/workflows/:id      → get workflow by ID
PUT    /api/workflows/:id      → update workflow
DELETE /api/workflows/:id      → delete workflow
```

### NL Generation (v0.0.1)

Single API endpoint. Uses whichever capable model the user has configured (prefers GPT-4o or Claude Sonnet). System prompt includes: tool catalog, model catalog, example workflows, the workflow JSON schema.

```
POST /api/workflows/generate
Body: { "description": "I need a team that...", "model": "gpt-4o" }
Response: { "workflow": { ... }, "explanation": "I created 3 agents..." }
```

### Settings Storage (v0.0.1)

Local config file (`~/.agentos/settings.json`). Contains API keys (encrypted at rest), default model preferences, workspace directory path. No cloud sync.

### Code Execution Sandbox (v0.0.1)

Python subprocess with timeout, memory limit, and restricted filesystem access. NOT a container — that's too heavy for local-first. Use `subprocess` with `resource` limits on Linux/Mac. Windows: basic process timeout.

For cloud deployment (later), switch to container-per-execution (Docker/Firecracker).

### Google/Slack Integration Auth (v0.0.1)

OAuth2 flow for Google Workspace. Users click "Connect Google Account" in Settings, complete OAuth, token stored locally. Slack: Bot token or user token entered in Settings.

## Success Criteria for v0.0.1

A user should be able to:

1. Start the platform locally with one command
2. Browse template gallery and pick "Research Report"
3. See the workflow in the visual builder with 4 pre-configured agents
4. Change the writer's model from GPT-4o to Claude Sonnet
5. Edit the researcher's behavior to "Focus on academic sources only"
6. Click "Run" and watch the agents execute in the monitoring dashboard
7. See the final report artifact in the workspace browser
8. Alternatively: describe a custom workflow in natural language and have it generated
9. Alternatively: build a workflow from scratch using drag-and-drop
10. All of the above works with OpenAI, Anthropic, or Ollama models
