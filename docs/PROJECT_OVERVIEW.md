# AgentOS — Project Overview

## The Vision

We are entering an era where AI agents are no longer simple chatbots that answer questions. They are autonomous systems that can operate on a user's machine — reading and writing files, browsing the internet, executing code, calling APIs, connecting to external services through MCP servers, and making complex decisions independently. Tools like Claude Code, Open Claw, Devin, and Codex have demonstrated that a single AI agent, given the right tools and context, can perform real work that previously required a human sitting at a keyboard.

But here is the problem: these agents work alone.

A user running Claude Code gets one agent doing one thing. If they want a second agent doing something different — say one agent researching a topic while another writes code based on that research — they open a second terminal, manage it separately, copy outputs between them manually, and hope the two don't step on each other. There is no way to tell these agents they are part of the same project. There is no way to define that one agent's output should feed into another agent's input. There is no way to say "wait for my approval before moving to the next step." There is no single place to see what all of your agents are doing, what they have produced, and what they are costing you.

AgentOS exists to solve this problem.

AgentOS is the governance and operating system for autonomous AI agents. Not metaphorically — structurally. A traditional operating system manages processes: it schedules them, allocates resources, isolates them from each other, provides inter-process communication, enforces permissions, monitors health, and gives the user visibility into what is running. AgentOS does the same thing, except the processes are autonomous AI agents. It is the management layer that sits above individual agent instances and gives the user full control over what each agent does, how agents work together, and what is happening at every moment. And critically, it governs them — enforcing security policies, capability boundaries, budget constraints, and human approval requirements so that autonomous agents operate safely within defined limits.

This is a fundamentally different layer than what most "multi-agent frameworks" provide. The current landscape has two distinct tiers of agent orchestration. The first tier — occupied by tools like CrewAI, AutoGen, and LangGraph — orchestrates prompt chains. An "agent" in these frameworks is a Python object with a system prompt; when it "runs," it makes an LLM API call and returns a string. The framework chains these calls together in sequences or graphs. This is sophisticated function composition, but the "agents" have no real processes, no persistent state, no file systems, and no operational independence. The second tier — the one AgentOS occupies — orchestrates actual autonomous runtimes. The agents are real running processes on a machine: Claude Code sessions with terminal access, Open Claw instances with code execution, Codex agents with cloud sandboxes. They persist over time, accumulate context, make independent decisions, and interact with the world through tools, APIs, and file systems. Orchestrating these systems requires fundamentally different infrastructure than chaining API calls — it requires an operating system.

The central idea is straightforward: a user should be able to take any number of autonomous agent instances — whether they are Claude Code sessions, Open Claw instances, agents powered by OpenAI's API, locally-run open source models, or any combination of these — and organize them into a coherent system where each agent has a clear role, agents collaborate through shared workspaces and direct communication, the execution follows a defined workflow with human checkpoints, and everything is observable and controllable from a single interface.

This is not a prompt chaining tool. The agents AgentOS manages are not lightweight wrappers around a single LLM API call. They are full autonomous systems with their own tool access, filesystem capabilities, decision-making loops, and operational independence. AgentOS does not replace these agents or try to build a better version of Claude Code. It takes agents that already exist and already work well individually, and makes them work together.

The long-term vision extends beyond technical users. AgentOS aims to be accessible to both audiences: a software engineer should be able to define workflows in YAML, manage them from the command line, write custom agent adapters, query the raw event log, and build programmatic integrations against the API. A project manager who has never written a line of code should eventually be able to open AgentOS, drag agents onto a canvas, connect them into a workflow, describe each agent's role in plain English, and hit run. Both users would interact with the same underlying framework — one through code and configuration, the other through a visual interface that facilitates and guides. Neither should feel like the tool was not built for them.

In practice, these audiences will be served sequentially. The first version of AgentOS targets technical users: CLI, YAML configuration, and programmatic API. This is the audience that will adopt first, provide the most actionable feedback, and stress-test the framework most aggressively. The visual workflow builder for non-technical users is a later milestone, built after the core framework is stable and the interaction patterns are well-understood from real technical usage. Building a visual interface that is genuinely usable by non-technical people — not just a DAG editor with a nice skin, but something that handles error states, provides meaningful feedback, and does not require understanding what a "system prompt" or "token budget" is — requires dedicated UX research and iteration that is better informed by a mature, stable backend.

## How AgentOS Thinks About Agents

The word "agent" is used loosely in the AI industry. For AgentOS, an agent has a specific meaning: it is an autonomous AI system capable of operating on a user's machine or environment. It can read and write files. It can execute commands. It can access the internet. It can connect to external services through APIs and MCP servers. It can make decisions about what to do next without being told every step. Critically, it runs as its own process with its own context, tools, and capabilities — it is not a function that gets called and returns a string.

Examples of what AgentOS considers an agent include Claude Code sessions, Open Claw instances, Devin sessions, OpenAI Codex agents, and custom agent implementations built with any framework. The key property is autonomy: the agent receives a task, decides how to approach it, uses its tools to execute, and produces a result. AgentOS does not micromanage the agent's internal decision-making. It assigns the task, monitors progress, collects the output, and coordinates with other agents.

AgentOS is deliberately agnostic about what powers an agent. The framework defines an Agent Adapter interface — a standard contract that any agent system can implement to participate in AgentOS orchestration. Built-in adapters will ship for common agent tools like Claude Code and Open Claw. But users are free to write their own adapters for any agent system, including agents powered by cloud API models from OpenAI, Anthropic, Google, or Mistral, agents running on local models through Ollama or vLLM, agents connecting to private enterprise deployments, or entirely custom agent implementations. A single workflow can mix agents from different providers — a Claude Code instance handling code, a GPT-4o-powered agent handling research, and a local Llama model handling data processing that cannot leave the user's machine. AgentOS orchestrates them all through the same mechanisms regardless of what is running underneath.

This adapter model also means AgentOS is future-proof. As new autonomous agent tools appear — and they will, rapidly — they simply need an adapter to participate in the ecosystem. AgentOS does not need to anticipate every possible agent implementation. It defines the contract, and any agent that fulfills that contract can be managed, teamed, monitored, and orchestrated like any other.

It is important to be honest about the difficulty here. Not all agent runtimes are equally easy to integrate. Many of today's autonomous agent tools — Claude Code, Open Claw, Devin — were not designed to be embedded as managed runtimes within an orchestration framework. Their interfaces change, their permission models differ, and some carry security constraints that make casual integration risky. AgentOS addresses this through a tiered adapter model. Tier 1 adapters cover agents that AgentOS fully controls — its own runtime, API-based agents, and sandboxed task executors. These adapters are first-class, well-tested, and provide the full range of management capabilities. Tier 2 adapters cover semi-controlled integrations — agent tools with stable APIs and supported extension points, where AgentOS can provide reliable orchestration with some limitations. Tier 3 adapters are best-effort wrappers around third-party CLIs and tools, where the integration surface is fragile and the level of control is limited. Tier 3 adapters are explicitly experimental — useful for early exploration but not suitable for production workflows where reliability is critical. This tiered approach is pragmatic. It avoids overpromising universal compatibility while still providing a clear path for integrating any agent system, with appropriate expectations about what each integration tier can deliver.

## Creating and Customizing Agents

AgentOS does not only orchestrate agents — it makes it easy to create and customize them.

The starting point is almost always an existing agent tool. A user might want a Claude Code instance configured as a financial researcher, or an Open Claw instance set up as a code reviewer, or a lightweight agent powered by a local Llama model that handles data formatting. These are all the same underlying tools that already exist and already work — but out of the box, they are general-purpose. Claude Code is a capable coding assistant, but it is not a financial researcher until someone tells it to be one, gives it the right tools, and scopes its access appropriately. AgentOS is the layer that makes this customization simple and repeatable.

Creating an agent in AgentOS means taking an agent backend — Claude Code, Open Claw, an API model, a local model — and layering on top of it the configuration that turns it into a specific worker. This configuration has four dimensions: behavior, tools, permissions, and constraints.

Behavior defines what the agent should do and how it should think. This is the agent's role description and system prompt — the instructions that shape its focus, personality, and approach. AgentOS provides two ways to set this. Non-technical users describe the agent's role in plain English: "You are a macro researcher. Focus on central bank policy decisions, inflation trends, and labor market data. Produce a structured summary with key findings and their market implications." AgentOS translates this into the appropriate system prompt and configuration for whatever agent backend is being used. Technical users can edit the system prompt directly, adjust model parameters like temperature, select persona presets, and add few-shot examples for precise control over behavior. Either way, the result is the same: a Claude Code instance that was a general-purpose assistant is now a focused macro researcher that stays in its lane.

Tools define what the agent can do beyond reasoning. A general-purpose Claude Code instance has access to everything — file system, terminal, web browsing. That is powerful but dangerous in a multi-agent system where you want each agent to have a scoped set of capabilities. AgentOS lets users control exactly which tools each agent has access to. A research agent might get web search and read-only file access. A code-writing agent might get full filesystem access and terminal execution but no internet. A compliance agent might get access to regulatory databases and document search but no ability to write code or modify files. AgentOS provides a catalog of built-in tools — web search, file read/write, code execution, API calls, database queries, MCP server connections, domain-specific integrations — and users select which ones each agent is allowed to use. Users can also register their own custom tools, pointing at any REST API, MCP server, or local script, and make them available to their agents.

Permissions control what the agent can access within the workspace and beyond. This goes deeper than tools. An agent with the "file write" tool might still be restricted to writing only in a specific folder. An agent with web access might be restricted to a whitelist of domains. An agent might require explicit human approval before performing certain actions — deleting files, making API calls that cost money, or publishing content. This layered permission model means that agents operate in sandboxed environments appropriate to their role. The user defines the boundaries, and AgentOS enforces them regardless of what the underlying agent tool would normally allow.

Constraints define the operational limits. How many tokens the agent can consume, how many API calls it can make, how long it can run, how much it can spend. These are hard limits, not guidelines. When a constraint is reached, the agent stops cleanly. This prevents runaway costs, infinite loops, and resource exhaustion. Users set constraints per agent, per team, or per workflow, and AgentOS enforces them at every level.

The key insight is that AgentOS does not build agents from scratch — it takes powerful general-purpose agent tools that already exist and gives users a structured way to specialize them. A Claude Code instance becomes a "Market Scanner" by giving it a focused system prompt, web search and financial data tools, read-only workspace access, and a reasonable token budget. An Open Claw instance becomes a "Code Reviewer" by giving it file read access, code execution, git tools, and instructions to focus on bugs, security, and style. The underlying agent tools provide the autonomy and capability. AgentOS provides the customization, scoping, and governance that turn them from general assistants into purpose-built workers.

AgentOS also supports agent templates — pre-configured agent definitions that users can instantiate and customize. A template for a "Financial Researcher" might specify Claude Code as the backend, include web search and document analysis tools, set a system prompt focused on market research, and define sensible budget limits. The user can deploy this template as-is or adjust any aspect of it — swap the backend to Open Claw, add a custom MCP server for proprietary data, tighten the permissions, change the focus from equities to crypto. Templates lower the barrier to entry: instead of configuring every dimension of every agent from scratch, users start from a proven foundation and customize to their needs.

## Teams and Collaboration

Individual agents are useful. Teams of agents are transformative.

AgentOS introduces the concept of a Team as a first-class primitive. A team is a named group of agents working toward a shared objective. Each agent in a team has a defined role — what they are responsible for, what tools they have access to, what constraints they operate under, and what they are expected to produce. Teams also define how their agents communicate: through a shared workspace where all agents can see the same files and artifacts, through direct messaging where agents can send information to specific teammates, or through both.

The team concept maps naturally to how humans organize work. A research department has researchers, analysts, and writers. A software team has architects, developers, and testers. A financial operation has traders, risk managers, and compliance officers. AgentOS lets users replicate these structures with AI agents, assigning each agent a clear responsibility and letting the framework handle coordination.

Teams can also work with other teams. A Research Team produces findings that feed into an Analysis Team, which produces recommendations that feed into an Operations Team. AgentOS defines these inter-team relationships through workflows — directed graphs that specify execution order, data flow, and human checkpoints between teams and individual agents.

## Inter-Agent Communication

Agents in AgentOS communicate through two complementary mechanisms, each suited to different kinds of collaboration.

The first is indirect communication through the workspace. An agent produces a file — a research summary, a dataset, a report — and downstream agents read it. This is the primary mechanism for most structured workflows, and it has significant advantages. It is simple, auditable (every file change is an event in the log), and naturally compatible with the DAG execution model where one task's output becomes the next task's input. It is also how real human teams communicate much of their work — through shared documents, spreadsheets, and repositories rather than through real-time conversation.

The second is direct communication through message channels. AgentOS provides a broker-mediated messaging system where agents can publish and subscribe to named channels. A channel is a topic — "research-findings", "risk-alerts", "data-ready" — that one or more agents can write to and one or more agents can listen on. All messages pass through AgentOS as the broker, which means every message is logged as an event, subject to permissions, and visible in the monitoring dashboard. Agents never communicate outside the framework's visibility.

Message channels enable a pattern that workspace-based communication alone cannot: progressive, asynchronous collaboration. In a strict DAG, a research agent must finish entirely before the analysis agent can begin. With channels, a research agent can publish partial findings as it goes — "initial macro data is ready at /research/macro_v1.md" — and the analysis agent can start working immediately while the researcher continues. This mirrors how real teams operate. Nobody waits for the complete research report before starting analysis. They begin as soon as there is enough to work with.

The routing of messages — deciding which agents should receive which messages and what actions should be triggered — can operate at two levels. Simple, predictable routing is rule-based: messages on channel X go to all agents subscribed to channel X. This is fast, deterministic, and sufficient for most workflows. For more complex coordination, AgentOS supports an optional manager agent — an agent whose role is not to perform domain work but to coordinate the team. The manager reads messages, decides where they should be routed, determines whether downstream tasks should be triggered, and handles ambiguous situations that simple rules cannot resolve. When even the manager cannot confidently decide — an ambiguous message, a conflict between agents, an unexpected situation — it can escalate to the human through a gate. This creates a natural escalation path: rules handle the obvious cases, the manager handles the complex cases, and the human handles the edge cases.

This communication model means AgentOS supports two complementary orchestration modes. Structured DAG workflows handle known, predictable processes where the sequence of tasks and their dependencies are defined in advance. Channel-based coordination handles dynamic, reactive processes where the flow of work depends on what agents discover as they operate. A single workflow can mix both — a DAG defines the overall structure, while channels allow agents within that structure to collaborate asynchronously and respond to intermediate results without waiting for hard task boundaries. The specifics of the channel protocol, manager agent design, and the interaction between channels and DAG scheduling are areas of active design that will be shaped by real usage as AgentOS matures.

## Workflows and Orchestration

A workflow in AgentOS is the dependency graph that defines how execution proceeds across agents and teams. It specifies which agents run first, which agents wait for others to finish, where human approval is required before proceeding, and how data flows from one step to the next.

Workflows are not rigid scripts. They are structured plans that respect the autonomous nature of the agents within them. An agent in a workflow receives its task, has full autonomy in how it approaches that task, and produces its output. The workflow then routes that output to the next step — which might be another agent, a human approval gate, or a fan-out to multiple parallel agents.

The workflow engine supports the patterns that real work requires. Linear sequences, where one agent finishes before the next starts. Parallel execution, where multiple agents work simultaneously on independent tasks. Fan-out and fan-in, where one agent's output triggers several parallel agents that eventually converge. Conditional branching, where the next step depends on what the previous agent produced. Review loops, where an agent's output is evaluated and sent back for revision if it does not meet quality standards. And human gates, where execution pauses and waits for a person to review, approve, reject, or provide additional input before the workflow continues.

These workflow patterns are defined through configuration files and CLI for technical users, with a visual drag-and-drop builder planned for later versions. The underlying execution engine is the same regardless of interface: a DAG executor that respects dependencies, manages parallelism, enforces gates, tracks state changes as events, and provides real-time observability into what is happening.

### Workflow Verification

Before a workflow runs, AgentOS can statically analyze the DAG for structural problems — acting as a compiler for agent workflows that catches errors before execution rather than discovering them at runtime. The verifier checks for circular dependencies, agents with insufficient permissions to complete their assigned tasks, budget allocations that are mathematically insufficient given historical cost data for similar tasks, data dependencies where a downstream agent expects input that no upstream agent is configured to produce, and missing approval gates at critical decision points.

This is especially powerful in the enterprise governance context. A compliance officer reviewing a proposed workflow can see, before anything runs, a formal verification report: "This workflow is well-formed. All agents have the permissions they need. Budget allocations are sufficient based on historical data. There are no orphan dependencies. The approval gates cover all critical decision points." That kind of pre-execution assurance is not available in any competing framework, and it is highly valued in regulated environments where deploying an improperly configured workflow could have compliance consequences.

### Adversarial Validation

Current multi-agent frameworks treat every agent's output as trustworthy input for the next agent. This is dangerous. A research agent that hallucinates a data point passes that hallucination downstream, where it gets compounded and reinforced by every subsequent agent that builds on it. This is the cascading hallucination problem, and it is the most cited reliability concern about multi-agent systems.

AgentOS addresses this through adversarial validation as a native workflow primitive. A validator node is a dedicated agent role whose purpose is not to produce work but to challenge it. The validator receives the output of a predecessor, independently verifies claims against source data, checks for internal consistency, flags confidence levels, and produces a validation report. If the validation fails, the workflow can automatically trigger a retry, a revision loop, or escalation to a human gate.

Adversarial validation can be inserted at any point in a DAG. A simple workflow might have a single validator after the research phase. A high-stakes workflow might have validators after every agent, with strict thresholds for what constitutes a passing validation. The validator agent uses different tools, different prompts, and ideally a different model backend than the agent it is validating — it is a genuine second opinion, not the same agent checking its own work.

This directly addresses the core reliability promise of AgentOS. Safe agent operations means not just secure permissions and budget controls, but reliable outputs. An orchestration system that can catch a hallucinated data point before it cascades through four downstream agents is offering something no competitor currently provides. It is the kind of feature that makes a demo unforgettable: "Watch this validator catch a fabricated citation that the research agent produced, and automatically trigger a correction before it reaches the analyst."

## Human-in-the-Loop

AgentOS is built on the principle that autonomous agents should not make irreversible decisions without human oversight. This is not a limitation — it is a feature. The most valuable agent systems are the ones where humans and agents collaborate, each contributing what they do best.

Gates are the mechanism for this collaboration. A gate is a checkpoint in a workflow where execution pauses and waits for human input. There are two types. Approval gates pause after an agent completes its work and ask the user to review the output before the workflow proceeds. The user sees what the agent produced, and can approve it (allowing downstream agents to continue), reject it with feedback (causing the workflow to fail or triggering a revision loop), or edit the output directly before passing it downstream. Input gates pause and ask the user to provide information that an agent needs — text input, a decision, a parameter — before the agent can proceed.

Gates are optional. A user who trusts their agents can build a workflow with no gates at all and let it run to completion autonomously. But for workflows that involve real stakes — financial decisions, published content, code deployed to production — gates provide the safety net that makes the system trustworthy. The user remains in control. The agents do the heavy lifting, but the human has the final say at every critical juncture.

Beyond gates, AgentOS supports pause and resume at any point. A user can pause a running workflow, inspect the current state, review what agents have produced so far, and then resume execution or stop it entirely. This is possible because all state is derived from the event log — pausing simply means stopping the executor, and resuming means picking up where it left off with the full event history intact.

## Workspaces and Shared State

Agents in AgentOS collaborate through shared workspaces. A workspace is a directory on the user's machine where agents read and write files, store data, and produce artifacts. All agents within a team share the same workspace, which means they can see each other's work, build on each other's outputs, and maintain a consistent view of the project's state.

AgentOS tracks every file change within a workspace. When an agent creates a file, modifies a file, or reads a file, that action is recorded in the event log. The user can see at any moment which files exist, who created them, when they were last modified, and what the agent was doing when the change happened. This file tracking is not just for monitoring — it is the foundation for collaboration. When a downstream agent starts its work, AgentOS can tell it exactly what files its predecessors produced, giving it immediate context about what has already been done.

Workspaces also serve as the ground truth for a workflow. Rather than passing data between agents through abstract message channels, agents produce files and artifacts that subsequent agents can read directly. This is how humans collaborate on real projects — through shared documents, datasets, reports, and code repositories — and it is how agents in AgentOS collaborate too. The workspace is the shared reality that all agents operate within.

To make inter-agent handoffs reliable, AgentOS defines a structured task output protocol. When an agent completes a task, it produces not just raw files but a structured output manifest — a JSON schema with required fields for key findings, confidence levels, data sources consulted, open questions, and references to files produced. This protocol ensures that downstream agents receive organized, parseable context rather than unstructured file dumps that they must interpret from scratch. The quality of multi-agent collaboration depends entirely on the quality of handoffs between agents. An unstructured handoff — "here are some files, figure it out" — forces the downstream agent to spend context and reasoning on understanding what its predecessor did, rather than building on it. A structured handoff — "here are the three key findings, supported by these sources, with these open questions remaining" — lets the downstream agent start working immediately on what matters. This protocol is not optional overhead; it is a launch-critical mechanism that directly determines the quality of multi-agent outputs.

## Observability and Monitoring

A core requirement of AgentOS is that the user always knows what is happening. There are no black boxes.

Every meaningful action in AgentOS is an event. When an agent starts a task, when it calls a tool, when it produces output, when it creates a file, when a gate is triggered, when a user approves or rejects, when a budget limit is approached — all of these are events recorded in an append-only event log. This log is the single source of truth for the entire system. The current state of any workflow, agent, or team can be reconstructed at any time by replaying the events.

The event log feeds two monitoring surfaces. The web dashboard presents a real-time visual view: a DAG graph showing which agents are running, waiting, succeeded, or failed; a live event stream showing what is happening right now; file browsers showing what agents have produced; and cost dashboards showing token usage and API spending per agent, per team, and per workflow. The CLI provides the same information in a terminal-friendly format: `agentos status` shows the current state, `agentos events` streams events in real time, `agentos cost` shows spending.

For technical users, the event log is also directly queryable. Every event is stored in SQLite with a defined schema, and users can write their own queries, build custom analytics, or feed events into external monitoring systems. The event log is not just an implementation detail — it is a first-class interface.

Because all state is event-sourced, AgentOS can offer something no other framework provides: deterministic replay and time-travel debugging. A user who gets a bad output can rewind to any point in a workflow's execution, inspect the exact state of every agent at that moment, see exactly what inputs each agent received and what it produced, and understand precisely where things went wrong. This goes beyond post-mortem log reading — the user can modify the state at any point in the replay and re-execute from that point forward, observing how downstream agents would have responded to different inputs. Change the output of the research agent at step three and see how the analyst's conclusions would have differed. Replace a hallucinated data point with the correct value and verify that the rest of the workflow produces a sound result.

This is time-travel debugging for agent workflows — a diagnostic tool that transforms multi-agent systems from opaque black boxes into fully inspectable, replayable, and modifiable executions. For technical users, it is invaluable for understanding how complex multi-agent interactions produce their results. For governance, it provides the ability to demonstrate exactly what happened and why, down to the individual agent decision level.

## Budget and Governance

Autonomous agents operating on real work with real costs need constraints. AgentOS enforces budgets at every level.

Each agent can have limits on tokens consumed, API calls made, execution time, and total cost. Each team and each workflow can have aggregate budgets. When a budget is exceeded, execution halts cleanly — no silent overruns, no surprise bills. The user is notified, and the state is preserved so execution can be reviewed or resumed with adjusted limits.

Budget enforcement is not just about cost control. It is also about safety. An agent caught in a loop, making the same API call repeatedly, will hit its budget limit and stop rather than running indefinitely. An agent that starts consuming tokens at an unexpected rate will be caught by its budget before the cost becomes significant. These constraints make it safe to give agents autonomy — they can operate freely within their defined boundaries, and the boundaries are hard.

## Security and Safe Agent Operations

Security is the single most critical concern in AgentOS. This is not an exaggeration — it is an architectural reality. An orchestration layer that manages multiple autonomous agents, each with tool access, file system capabilities, network access, and independent decision-making, is by definition a **blast-radius concentrator**. If the orchestrator is compromised or misconfigured, every agent it manages is affected. If an agent escapes its boundaries, it operates with whatever capabilities the underlying runtime provides. Recent security research on tools like Claude Code and Open Claw has demonstrated that autonomous agent runtimes carry real and non-trivial security risks — config-driven execution paths, implicit trust boundaries, and repo-supplied instructions that can influence agent behavior. AgentOS sits above these systems. It must be more secure than any individual agent it manages, because it controls all of them.

This security requirement shapes the entire architecture and is a core part of what AgentOS offers. In a landscape where autonomous agents are powerful but risky, AgentOS positions itself as the safe way to run them — the layer that makes multi-agent operations governable, auditable, and controlled.

The first layer is process isolation. When AgentOS spawns multiple agent instances, each operates within enforced boundaries. An agent assigned to the Research Team cannot access the Operations Team's workspace, read another agent's credentials, or interfere with processes outside its scope. The degree of isolation scales with the deployment context — lightweight directory-scoping for a solo developer on a laptop, containerized sandboxes with per-agent namespaces for enterprise deployments handling regulated data. AgentOS enforces the permission boundaries regardless of the underlying isolation mechanism.

The second layer is a capability-based security model. Rather than coarse permissions like "this agent can write files," AgentOS supports fine-grained capabilities: this agent can write to `/workspace/research/*.md`, can read from `/data/market/**`, can make HTTP requests to `api.financialdata.com`, cannot execute shell commands, cannot access the network outside its whitelist. Capabilities are granted explicitly, revocable at any time, and auditable through the event log. This follows the same principle as modern OS security — Linux capabilities, iOS entitlements, Android permissions — where each process receives only the minimum privileges it needs to do its work. The result is that an agent's effective power is determined by its granted capabilities, not by what the underlying runtime would normally allow.

The third layer is runtime-verified policy enforcement. This is the difference between telling an agent not to do something and physically preventing it from doing it. Prompt-level restrictions — "do not access the internet" — are honor-system security. The agent might comply, or it might hallucinate a reason to ignore the instruction. Runtime-level enforcement means that an agent without the network capability literally cannot make HTTP requests, regardless of what the LLM decides to do.

It is important to be honest about what can be enforced at which level. For agents where AgentOS controls the tool-calling loop (Tier 1 adapters, API-based agents), runtime enforcement is straightforward — AgentOS intercepts every tool call and validates it against the capability set before execution. This is achievable in V1. For autonomous runtimes like Claude Code, which execute shell commands and make network requests through their own process, enforcement requires either sandbox-level isolation (containers, seccomp profiles, AppArmor) or tool-wrapping proxies. Sandbox-level isolation is robust but adds operational complexity; tool-wrapping is more fragile because autonomous agents can discover and use tools outside the wrapper's inventory. AgentOS will implement orchestration-layer enforcement in V1 — task assignment, workspace scoping, budget limits, tool allowlists — and add progressively stronger sandbox-level enforcement in subsequent versions as the infrastructure matures. The security architecture is designed to support both levels, and the capability model applies uniformly regardless of how enforcement is implemented underneath.

The fourth layer is credential management. Agents need API keys to connect to LLM providers, MCP servers, financial data services, and other external systems. These credentials must never appear in plain text in agent prompts, workspace files, event logs, or monitoring dashboards. AgentOS manages a secrets store where credentials are registered once and injected into agent environments at runtime through secure channels. Agents can use the credentials to authenticate with external services, but they cannot read, log, or exfiltrate the raw keys. When an agent is terminated or its permissions change, its access to credentials is revoked immediately.

The fifth layer is data isolation between teams and workflows. A workspace is scoped — agents within a team share their team's workspace, but they do not have implicit access to other teams' data. When data needs to flow between teams, it passes through the workflow's defined data channels, which are logged and subject to permissions. Shared datasets that multiple teams need can be mounted as read-only resources, visible to all but modifiable by none. This prevents accidental data contamination and ensures that each team's workspace reflects only what it is supposed to see.

The sixth layer is audit and compliance. The event log provides a complete, immutable record of every action taken by every agent — every tool call, every file access, every capability exercise, every policy enforcement decision. For regulated domains — finance, healthcare, legal — this audit trail satisfies compliance requirements: data retention policies, proof that approval gates were enforced, records of who accessed what data and when, evidence that security policies were active and enforced throughout execution. The event log is not just monitoring — it is the compliance artifact.

Security is not a feature of AgentOS. It is the foundation that makes everything else trustworthy.

## Reliability

AgentOS must be extremely reliable. This is not a prototype or a research project — it is the foundation for systems that manage real work with real consequences. Engineering teams will use it to orchestrate development pipelines. Financial applications will use it to manage investment research and analysis. Future deployments may manage research workflows, business operations, or security incident response. In all of these cases, silent failures, lost state, or undefined behavior are unacceptable.

This reliability requirement drives several architectural decisions. All state is event-sourced, meaning it can be reconstructed from the log at any time and no state is lost if a process crashes. All agent interactions go through typed interfaces with schema validation — no untyped dictionary passing, no implicit contracts. All errors are surfaced explicitly through events — nothing fails silently. All budget limits are enforced as hard constraints, not suggestions. The system is designed so that at any moment, a user can ask "what is happening and why" and get a complete, accurate answer from the event log.

## Error Handling and Recovery

When an agent fails a task, AgentOS does not simply report the failure and stop. It provides the user — and optionally the framework itself — with a toolkit for deciding what happens next. This mirrors how real organizations handle failures: a manager does not shut down the entire department because one employee made a mistake. They assess the situation, decide whether to retry, reassign, adjust scope, or escalate, and keep the operation moving.

AgentOS supports several recovery strategies. The simplest is retry — run the same agent on the same task again, on the assumption that the failure was transient (a network timeout, a rate limit, a temporary API error). Retries can be configured with limits and backoff intervals so the system does not hammer a failing service. The next strategy is fresh restart — terminate the agent instance and spawn a new one with a clean context, then retry the task. This addresses the "spoiled context" problem discussed elsewhere: if the agent failed because its context had degraded, a fresh instance with a curated briefing may succeed where the degraded one could not. Beyond restart, there is fallback — route the task to a different agent entirely. A task that failed on a Claude Code instance might be retried on an Open Claw instance, or on a cheaper model that handles the specific task type well enough. Finally, there is graceful degradation — mark the failed branch as incomplete and continue the workflow with whatever results are available, rather than failing the entire operation because one branch could not deliver.

Users define recovery policies per task, per agent, or per workflow. A policy might say: "Retry up to three times with exponential backoff. If still failing, restart with a fresh instance. If the fresh instance also fails, fall back to model X. If that fails, skip this branch and continue with partial results." These policies are part of the workflow configuration, visible in the builder, and logged as events when they are triggered. The user can also intervene manually at any point — a failed task can surface as a gate where the human decides what to do rather than relying on automated policies.

The goal is that agent failures are expected, managed events rather than catastrophic surprises. In a system with many agents running complex tasks, some failures are inevitable. What matters is that the framework handles them gracefully, gives the user visibility into what happened and why, and provides clear paths to recovery.

## Extensibility

AgentOS is a framework, and frameworks must be extensible at every layer. The agent adapter model — the ability to plug in any agent system by implementing a standard interface — is one dimension of extensibility, but not the only one.

Users and developers can register custom tools that agents can use, pointing at any REST API, MCP server, or local script. They can define custom event handlers that trigger actions when specific events occur — sending a Slack notification when a gate is waiting for approval, posting to a webhook when a workflow completes, feeding events into an external monitoring system. They can create custom workflow node types beyond the built-in agent and human input nodes. And for technical users building on the programmatic API, everything the web dashboard does is available as a REST endpoint, enabling custom integrations, automation scripts, and third-party tooling that extends AgentOS in ways the core framework does not need to anticipate.

The principle is that AgentOS provides strong, opinionated defaults for common use cases while leaving every layer open for customization. Users who need the defaults get a complete, working system out of the box. Users who need something different can extend, replace, or build on top of any component without forking the framework.

## Strategy and Business Model

AgentOS follows the Linux model of development. Linux is a kernel — a foundational piece of infrastructure that does nothing useful on its own. Its value comes from the systems built on top of it: Android, Ubuntu, cloud infrastructure, embedded devices, supercomputers. Linux proved itself not through a whitepaper or a demo, but through real products that depended on it and pushed it to be reliable, performant, and complete. The kernel earned trust by being the foundation that serious systems could not afford to have fail.

AgentOS takes the same approach. The framework is the kernel — the orchestration, monitoring, and management infrastructure that any multi-agent system can be built on. But a framework without a real product built on it is just a spec. It has not been tested under pressure. Its APIs have not been shaped by the demands of actual users solving actual problems. Its reliability claims are theoretical. To make AgentOS genuinely good, it needs to be forged by building something real on top of it.

This is the kernel. It is domain-agnostic by design. Nothing about AgentOS knows or cares about finance, software development, research, or any other field. It provides the infrastructure for creating, running, orchestrating, and monitoring autonomous agents, and it does this well.

Critically, this is not a build-from-scratch effort. The core kernel — event log, DAG executor, task state machine, budget manager, workspace management — is already implemented and tested with over 400 passing tests. V1 development continues from this existing foundation, focusing on completing, hardening, and shipping an already-in-progress system rather than starting from zero. This materially changes the feasibility calculus for the 6-month timeline.

A scoped V1 focuses on getting the core right rather than trying to support everything at once. This means starting with one primary agent class — coding and engineering agents, which have the most mature tooling and the clearest demand — and one runtime model: locally managed processes. Tier 1 adapters (fully controlled agents) and Tier 2 adapters (stable integrations like Claude Code) are the priority. Tier 3 adapters (best-effort third-party wrappers) are explicitly experimental. AgentOS has four potential competitive moats, each of which strengthens over time:

The first is control-plane lock-in through the event log. For organizations in regulated industries, this switching cost is significant.

The second is the adapter ecosystem. If AgentOS becomes the standard orchestration layer, third-party agent developers and tool providers are incentivized to build and maintain adapters because it gives them distribution. A healthy adapter ecosystem makes AgentOS the default place where new agent tools become available to orchestrated workflows.

The third is enterprise governance. Policy enforcement, capability-based security, secrets management, approval workflows, audit trails, and least-privilege agent operations — this is where enterprise buyers pay. Security and governance features are hard to build well and hard to switch away from once adopted.

The fourth is workflow performance data. Over time, AgentOS accumulates data about which agent configurations, team compositions, and models produce the best results for which tasks. This data creates a network effect: the more workflows run on AgentOS, the better its recommendations become, and the more valuable the platform is to each user.

While the long-term vision includes making AgentOS available as open-source infrastructure, the scope and ambition of the project require starting as a closed-source product. The pragmatic path is to develop AgentOS as a closed-source product initially, targeting both technical and non-technical users as paying customers. The dual-audience design is a strength here — a product that serves developers through APIs and CLI while also serving business users through a visual dashboard has a broader addressable market than a developer-only framework. This makes AgentOS more attractive to investors, who see a product with a clear revenue model and a large potential user base rather than an open-source project searching for monetization.

The current plan is a practical hybrid: V1 launches with a closed core and open-source adapters, example workflows, and CLI tools. Open-source adapters give developers something to evaluate, build trust, and create an upgrade path to the full platform. The core remains closed to protect the primary value — governance, security enforcement, workflow engine, event log infrastructure — while the open components drive adoption and community engagement.

The core open-source decision will be revisited at V1.5, informed by adoption data, competitive dynamics, and community demand. If an open-source competitor emerges with similar governance positioning, the timeline may accelerate. The architecture is modular enough that components can be open-sourced independently — the adapter interface, workflow schema, and event format can all be opened without exposing the enforcement and orchestration internals.

This is the Linux playbook. Build the kernel, build something serious on it, let that pressure make the kernel excellent, then release the kernel for the world to build on. The DevOps demo is the showcase that attracts developers. The hedge fund is the crucible that forges reliability. Together they prove that AgentOS is not another framework — it is infrastructure.

## Future Discussion

The following areas are not yet fully designed but represent important challenges that AgentOS will need to address as the framework matures. They are recorded here to anchor future exploration.

### Context Management and Knowledge Infrastructure

Autonomous agents are powerful, but they are bounded by what they can hold in context. A Claude Code session has a finite context window. A research agent that has been running for hours may have accumulated thousands of pages of findings, but it can only reason about a fraction of that at any given moment. As workflows grow more complex — more agents, longer execution times, richer data — the question of how agents access and retain knowledge becomes critical.

The naive approach is to pass everything as raw text. This works for small workflows but collapses quickly. A downstream agent that receives the full unfiltered output of three upstream agents may spend most of its context window on information it does not need, pushing out the details that actually matter. Worse, large contexts tend to degrade agent performance — important instructions get lost in the noise, and the agent starts missing things it would catch in a shorter, focused prompt.

AgentOS needs a knowledge infrastructure layer that sits between agents and their data. The most promising direction is retrieval-augmented generation — rather than stuffing everything into the prompt, agents query a knowledge store and retrieve only the fragments relevant to their current task. But basic RAG (embed documents, search by similarity, paste top results) has well-documented limitations: it misses connections between related concepts, struggles with multi-hop reasoning, and often retrieves text that is superficially similar but not actually useful.

Several more advanced approaches deserve investigation. Knowledge graphs offer structured representations of entities and relationships that agents have discovered. Instead of searching for similar text chunks, an agent can traverse a graph: "What did the macro researcher find about interest rate policy? What companies did the sector analyst flag as sensitive to rate changes? What is the historical correlation?" This kind of structured reasoning over accumulated knowledge is something flat vector search cannot do well. Combining knowledge graphs with embedding-based retrieval — using the graph to guide what gets retrieved and the embeddings to find the right passages — is a direction worth exploring seriously.

There is also the question of persistent knowledge bases that span multiple workflow runs. Tools like NotebookLM have demonstrated that a curated collection of documents can serve as a surprisingly effective knowledge backend. Users are already experimenting with connecting agents to NotebookLM instances via MCP servers, essentially giving the agent a managed research library that it can query conversationally. AgentOS could formalize this pattern — allowing users to attach knowledge bases to agents or teams, where the knowledge base accumulates findings across runs and serves as institutional memory. A research team that runs every morning does not start from zero each time. It builds on what it learned yesterday, last week, last month.

The practical questions are significant. How does the knowledge base stay accurate as information becomes stale? How do agents know when to query external knowledge versus relying on what is already in their context? How do we avoid the failure mode where an agent retrieves confident-sounding but outdated or incorrect information and treats it as ground truth? How do we handle knowledge conflicts — when two sources disagree, or when a new finding contradicts something stored in the knowledge base? These are hard problems, and getting them wrong can be worse than not having a knowledge layer at all, because bad retrieval gives agents false confidence.

The goal is not to solve all of this immediately. The goal is to design AgentOS with the right abstractions so that knowledge infrastructure can be plugged in, experimented with, and improved over time without requiring changes to the core framework. Agents should interact with knowledge through a defined interface, and the implementation behind that interface — whether it is simple RAG, a knowledge graph, a NotebookLM-style managed library, or something that has not been invented yet — should be swappable.

Beyond within-run context, there is the question of cross-run memory. When a research team runs the same workflow every morning, does it start from scratch each time, or does it remember what it found yesterday? In the current model, each run is stateless — agents receive their configuration and task, execute, and produce output, with no awareness of previous executions. But real teams accumulate institutional knowledge. A macro researcher who has been tracking interest rate policy for months has context that a new hire does not. A compliance agent that reviewed last quarter's reports understands the firm's patterns and edge cases in a way that a fresh instance cannot.

AgentOS could formalize cross-run memory as a persistent store attached to agents, teams, or workflows. After each run, the system extracts key findings, decisions, and outcomes and writes them to the store. Before the next run, it injects a curated summary of relevant prior knowledge into the agent's context. The challenge is curation — blindly injecting everything from prior runs recreates the context bloat problem. The system needs to determine what is still relevant, what has become stale, and what level of detail is appropriate. This is another area where knowledge graphs could prove valuable: a structured representation of accumulated knowledge is easier to query selectively than a flat archive of past outputs.

There is also the possibility of learning from outcomes. When a user rejects an agent's output at an approval gate and provides feedback — "too speculative, stick to data-backed claims" — that feedback is currently lost after the run ends. But it represents a direct signal about what the user values and what the agent should do differently. AgentOS could store this feedback and use it to adjust future runs: tightening the agent's system prompt, adding constraints, or injecting the feedback as a reference that shapes the agent's behavior without requiring the user to manually update the configuration. Over time, the system learns the user's preferences and standards, and agents get better at producing outputs that pass approval on the first attempt.

The most ambitious extension of this idea is workflow-level learning. Beyond individual agents improving, can the system learn which workflow configurations produce the best results? AgentOS has a unique vantage point: it observes every run, every agent's performance, every approval and rejection, every cost and duration, across every workflow the user has ever executed. This data contains patterns. Perhaps a three-agent research team consistently produces better outputs than a two-agent one. Perhaps Claude Code performs better in the analyst role than GPT-4o for this particular user's domain. Perhaps workflows with an approval gate after the research phase have higher final approval rates than those that skip it. Perhaps certain team compositions — a specific combination of agent backends, roles, and tool configurations — reliably outperform others for a given type of task.

If AgentOS can surface these patterns, it moves from being a passive orchestration tool to an active advisor. "Based on your last twelve research workflows, teams with a dedicated fact-checker agent had 40% fewer rejections at the final gate. Would you like to add one?" Or further: "For market analysis tasks, here is the team composition that has historically produced the best results for users with similar preferences." This is the beginning of optimal team discovery — the system learning, from accumulated evidence across many runs and potentially many users, which configurations work best for which kinds of tasks, and suggesting or even auto-configuring teams based on the user's needs.

This is speculative and far-future, but it represents a compelling long-term direction. The foundation for it is already present in the architecture: the event log captures everything needed to analyze workflow performance, and the adapter model means the system has visibility into which backends, models, and configurations were used in each run. The question is building the analysis and recommendation layer on top of that data, and doing so in a way that respects user privacy and preferences.

### Agent Health, Degradation, and Instance Lifecycle

Autonomous agents are not deterministic systems. They are probabilistic, and their behavior can degrade over time within a single session. This is a problem that anyone who has used Claude Code or similar tools for extended periods has encountered: the agent starts strong, but after enough turns, enough context accumulation, enough back-and-forth, it begins to lose coherence. It forgets instructions it followed perfectly an hour ago. It starts hallucinating file paths or function names. It makes confident assertions about things it has not verified. It gets stuck in loops, trying the same failing approach repeatedly. The agent has not changed — the same model is running — but its effective performance has degraded because its context has become cluttered, contradictory, or simply too large for it to reason about clearly.

In the industry, this is sometimes called a "spoiled" context. The agent's working memory has accumulated enough noise, dead ends, and self-referential confusion that it is no longer operating at its potential. For a single-agent scenario, the user notices and starts a fresh session. But in a multi-agent orchestration system, this is much harder to catch and much more dangerous. A degraded agent in a team is producing outputs that downstream agents will consume and reason about. Bad outputs cascade. A hallucinated data point from a research agent becomes a false assumption in an analysis agent, which becomes a flawed recommendation from a strategy agent. The system does not just degrade — it degrades with confidence, because each downstream agent treats its predecessor's output as reliable input.

AgentOS needs to address this at multiple levels.

The pragmatic approach to this problem is not to attempt perfect automated detection of degradation — that is a research problem with noisy signals and no reliable solution today. Instead, AgentOS should focus on what is actionable: policy-based lifecycle management and aggressive structured artifacting.

The first level is prevention through lifecycle policies. AgentOS should make it easy for users to configure when agent instances are restarted. A user might decide that research agents should be restarted every N turns, or every N tokens of accumulated context, or after every major task boundary. The restart is not a failure — it is maintenance. Just as a responsible system administrator reboots servers on a schedule to clear accumulated state, a responsible agent orchestrator can restart agent instances to maintain context quality. The fresh instance inherits the completed work through the workspace (files, artifacts, structured data) and through a framework-generated briefing, but it does not inherit the context drift. This is simple, predictable, and effective against the most common degradation patterns.

The second level is structured artifacting. The reason context degrades is that agents accumulate unstructured reasoning, dead ends, and internal state that clouds their working memory. If agents are configured to externalize their progress — writing structured summaries, intermediate results, and key findings to workspace files at regular intervals — then the workspace becomes the durable record of progress, not the agent's context. A fresh instance can pick up exactly where the previous one left off by reading the artifacts, without inheriting any of the context noise.

The third level is manual intervention. Users who notice suspicious behavior — repetitive outputs, contradictions, hallucinated references — need the ability to terminate the agent instance and start a fresh one at any time. This is not the same as stopping and resuming. A resume picks up the existing context. A restart creates a new agent instance with a clean context, re-injects the relevant configuration (role, tools, permissions, constraints), and provides it with a curated summary of the work completed so far. AgentOS should make this restart operation simple and fast, so users are not hesitant to use it when something feels off.

There are also questions about how to handle mid-task restarts. If an agent is in the middle of a complex task when the user or framework decides it needs a fresh start, what happens? Does the new instance start the task over from scratch? Does it receive a checkpoint of progress? Can AgentOS decompose the original task into completed and remaining subtasks, marking the completed ones as done and assigning only the remainder to the new instance? These are workflow-level concerns that interact with the restart mechanism.

Finally, there is the question of user control versus automation. Some users will want full manual control: "I see this agent is acting weird, let me restart it." Others will want automatic lifecycle management: "Restart any agent that exceeds 50,000 tokens of accumulated context" or "Restart any agent that has been running for more than 2 hours." AgentOS should support both, with sensible defaults that prevent the worst degradation while giving users the ability to tune the behavior to their specific needs and risk tolerance.

### Agent Performance Benchmarking and Economics

No one in the ecosystem today has a rigorous, standardized way to answer the question: "Which agent, with which configuration, performs best on which type of task?" AgentOS is uniquely positioned to build this because it sits above the agents and observes everything — task descriptions, agent configurations, execution traces, outputs, human approval and rejection decisions, cost, and duration.

This could become a concrete feature: an automated benchmarking engine that, given a task type, runs it across multiple agent backends with identical inputs and evaluates the outputs against user-defined quality criteria. Over time, this produces empirical performance profiles per agent backend, per task category. Nobody else can build this because nobody else orchestrates heterogeneous agents through a unified observation layer.

The benchmarking engine transforms AgentOS from "a tool that runs agents" into "the tool that knows which agent to run." That is a fundamentally different value proposition. It also creates a data moat that compounds with usage — the more workflows that run on AgentOS, the richer the performance data, the better the recommendations, and the more valuable the platform becomes to each user.

At scale, this data becomes a market intelligence product. AgentOS sees the actual cost-performance profile of every major agent backend across real-world tasks. Which model produces better research summaries per dollar? How does Claude Code's output quality compare to Codex for code review tasks? Aggregating this data (anonymized) across the user base produces an "Agent Economics" benchmark — the definitive industry reference for agent cost-performance. This positions AgentOS as the authority on agent economics, attracts users who want to participate in the benchmark, and creates a data asset that no competitor can replicate without equivalent deployment scale.

### Agent Safety Score

AgentOS could introduce a quantified risk metric — an Agent Safety Score — that evaluates the security and governance posture of any agent deployment or workflow. The score would incorporate permission scope (how much can each agent do?), isolation level (how contained is the blast radius?), budget constraints (what is the maximum cost of a failure?), human oversight density (how many approval gates per critical decision?), adversarial validation coverage (what percentage of outputs are independently verified?), and historical reliability (what is this agent configuration's track record?).

The safety score would be visible in the dashboard for every workflow, and organizations could set minimum score thresholds for production deployments. Over time, this metric could become an industry standard — the way organizations evaluate whether an agent deployment meets their risk tolerance for a given context. It is both technically grounded (based on real architectural properties and enforcement mechanisms) and commercially leverageable (enterprises will pay for certification and compliance tooling built around measurable safety guarantees).

### Dynamic Team Composition at Runtime

The current model describes teams as statically defined: configure agents, assign roles, run the workflow. But real work is unpredictable. A research agent might discover mid-task that the problem requires expertise it does not have — a macro analysis reveals a regulatory dimension that needs a specialized compliance agent, or a code review uncovers a security vulnerability that needs a dedicated security analyst.

AgentOS could support dynamic team scaling — the ability for a workflow to spawn additional agents at runtime based on what earlier agents discover. An agent publishes a structured request ("I need a compliance specialist with access to SEC filings"), and the orchestrator either provisions one from a template catalog or escalates to the human through a gate. The workflow DAG mutates at runtime, with the new agent inserted as a dependency for downstream tasks.

This is architecturally complex but genuinely novel. No existing framework supports runtime-adaptive team composition. It moves AgentOS from static orchestration to adaptive orchestration — a qualitative leap in capability that is structurally difficult for competitors to replicate because it requires deep integration between the workflow engine, the adapter model, the template system, and the permission framework.

### Cross-Workflow Agent Specialization Through Fine-Tuning

AgentOS accumulates precisely the data needed to fine-tune models for specialized roles: system prompts, tool configurations, task descriptions, agent outputs, and human approval or rejection feedback with reasons. Over enough runs, this data could be packaged into fine-tuning datasets and used to create purpose-trained agent backends.

A "macro researcher" agent that started as a generic Claude instance with a system prompt gradually becomes a purpose-trained macro research model, fine-tuned on the user's actual data, feedback, and quality standards. This creates a flywheel: use AgentOS, generate training data, fine-tune specialized agents, get better results, generate better training data. The agents literally improve the more you use the platform. This is the strongest possible form of platform lock-in because the value is in the accumulated specialization, which cannot be exported or replicated on a competing platform.

This depends on model providers offering fine-tuning APIs (which some already do) and on accumulating sufficient data per task type. It is a long-term capability, but the data collection infrastructure — the event log, the structured task outputs, the approval feedback — should be designed from the start to support this future use case.

### Deployment and Multi-User Access

AgentOS is designed as a local-first system — it runs on the user's machine, manages agents that operate on that machine, and serves the web dashboard from localhost. This is the simplest deployment model and the right starting point: no cloud dependency, full data privacy, everything under the user's direct control. For a solo user managing a personal hedge fund or a developer orchestrating coding agents, local deployment is sufficient and ideal.

But not every use case fits a single machine with a single user. A financial firm with ten analysts might want a shared AgentOS instance where each analyst manages their own agent teams but the organization has centralized monitoring, shared workflow templates, and aggregate cost tracking. A research lab might want AgentOS running on a dedicated server that multiple researchers connect to, each with their own workspace and permissions but sharing compute resources and agent infrastructure. An enterprise might want containerized deployment across a cluster, with agents distributed across machines and orchestrated centrally.

These scenarios introduce questions that the local-first model does not face. Multi-user access requires authentication, authorization, and user-scoped isolation — one user's workflows, workspaces, and credentials must be invisible to another. Shared resources require allocation and quota management — how are agent instances, compute, and API budgets distributed across users? Centralized deployment requires decisions about server architecture, scaling, persistence, and high availability. Containerized deployment connects to the security isolation discussion — each agent in its own container provides strong boundaries but adds operational complexity.

The path from local-first to multi-user server deployment should be incremental. The core framework — the workflow engine, event log, agent adapters, and monitoring — does not need to change. What changes is the deployment surface: how the system is started, how users authenticate, how workspaces are scoped, and how resources are allocated. AgentOS should be designed so that these deployment concerns are layered on top of the core framework rather than entangled with it, making the transition from single-user local to multi-user server a matter of configuration and infrastructure rather than a rewrite.

This landscape is converging rapidly: AutoGen Studio already offers low-code multi-agent workflows; CrewAI markets a visual editor with enterprise workflow capabilities; Microsoft is positioning its Agent Framework as a unified orchestration successor; observability vendors are commoditizing parts of monitoring and cost control. The "multi-agent orchestration" idea is not novel. The differentiation window is compressing.

AgentOS must be clear-eyed about where it is genuinely different and where competitors are catching up.

The most defensible distinction is the Layer 1 vs Layer 2 divide. Most existing frameworks are Layer 1 — they orchestrate prompt chains. An "agent" is an LLM API call with a system prompt; the framework chains these calls together. AgentOS is Layer 2 — it orchestrates actual autonomous runtimes. The agents are real running processes with file access, tool use, network access, and persistent decision loops. This is not a marketing distinction. It is an architectural difference that determines what problems each system can solve. A prompt chain orchestrator cannot manage a Claude Code session that runs for two hours, produces forty files, and needs to be restarted when its context degrades. AgentOS can.

The second distinction is the security posture. As autonomous agents become more powerful and more prevalent, the security concern becomes urgent. Most existing frameworks provide minimal isolation, no capability-based permissions, and no runtime-verified policy enforcement. AgentOS makes safe agent operations a headline feature — not as an add-on but as the architectural foundation. In a landscape where every major autonomous agent tool has faced public security scrutiny, being "the safe way to run multi-agent systems" is a meaningful differentiator.

The third distinction is provider neutrality. Most frameworks are tightly coupled to specific LLM providers or ecosystems. AgentOS is deliberately agnostic through the adapter model — any agent system can participate, and a single workflow can mix agents from different providers.

The platform risk must be addressed directly: what happens when Anthropic ships native multi-agent orchestration in Claude Code, or when OpenAI expands Codex into a full multi-agent platform? This is not hypothetical — it is likely. The answer is that first-party platforms will optimize for their own agents within their own ecosystem. Anthropic will build orchestration for Claude agents. OpenAI will build orchestration for OpenAI agents. Neither will build the governance, security, and compliance layer that organizations need to run heterogeneous agents from multiple providers under unified policy control. AgentOS serves organizations that need provider independence for strategic or regulatory reasons, that need to mix agents from different providers in the same workflow, that need audit trails and capability enforcement that go beyond what any single provider offers, and that need on-premises deployment where their data never leaves their infrastructure. This positions AgentOS as enterprise governance infrastructure rather than a developer convenience tool — a harder market to enter but a far more defensible one, because governance requirements do not go away when a provider ships a new feature.

These distinctions are real today but cannot be taken for granted. Competitors will add features, first-party platforms will expand, and the landscape will continue to converge. The risk is building something that tries to be everything and ends up being a mediocre version of what focused tools do well. AgentOS must stay sharp on its identity: it is the operating system for autonomous agents — the secure, observable, provider-neutral control plane for real autonomous runtimes. Not another prompt chain framework with a different name.

## What AgentOS Is Not

AgentOS is not a chatbot framework. The agents it manages are not conversational assistants that answer questions. They are autonomous workers that perform tasks, produce artifacts, and operate on real systems.

AgentOS is not a prompt chain tool. It does not string together a sequence of LLM API calls and call it a workflow. The agents it orchestrates are full autonomous systems with their own tools, decision-making loops, file access, and operational independence. Each agent is a complete system in its own right.

AgentOS is not a replacement for existing agents. It does not compete with Claude Code or Open Claw or Devin. It makes them work together. If those tools are skilled workers, AgentOS is the organization that hires them, assigns them roles, and manages the project.

AgentOS is not exclusively for developers — but it starts with them. The first version targets technical users through CLI, YAML, and API. The visual interface for non-technical users is a later milestone, built on a stable foundation. The long-term vision is that both audiences are served equally through the same underlying framework.

AgentOS is not a Layer 1 framework. It does not orchestrate prompt chains or sequences of LLM API calls. It operates at Layer 2 — managing actual autonomous runtimes with real processes, real file access, real tool use, and real operational independence. This distinction is architectural, not cosmetic, and it determines the class of problems AgentOS can solve.
